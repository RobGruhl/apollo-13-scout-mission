Reading the numbers

  • Scouts reached ≈ how many kids. The /ping/view/index beacon fires once per device, ever — it needs JavaScript, so crawlers don't trip it, and the service worker never caches it. Each QR scan at the table lands here exactly once.
  • The service worker hides repeat visits. After the first load, the whole site is cached on the phone, so a scout replaying the mission offline generates no new traffic. First visits are counted reliably; browsing depth is undercounted.
  • How many finished = the two /ping/…completion/* rows above, added. How many of each victory = the four /ping/card/* counts — those already combine the classic mission and the Apollo Trail, since a trail winner walks up to the table for the same card.
  • The pings are all 404s on purpose. The site is static, so there's nothing to receive them — Cloudflare counts the request path at the edge and the 404 costs the scout nothing. Every one of them is disclosed on /privacy.html; if you change a beacon, change that page in the same commit.
  • This page is a snapshot, not a live view. The numbers are baked into the HTML — a static page can't hold the Cloudflare API token, so it can never refresh itself in the browser. The auto-refreshing dashboard lives at robgruhl.github.io/apollo-telemetry (separate repo, GitHub Actions + laptop dispatch, ~every 15–30 min). To refresh this snapshot, tell Claude "refresh the telemetry dashboard" or run ./scripts/ping-census.sh. Cloudflare's free plan keeps per-path detail for 8 days (queried one 24-h window at a time), so refresh at least weekly or the daily series loses its tail.
