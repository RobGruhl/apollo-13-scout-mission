Reading the numbers

  • Scouts reached ≈ how many kids. The /ping/view/index beacon fires once per device, ever — it needs JavaScript, so crawlers don't trip it, and the service worker never caches it. Each QR scan at the table lands here exactly once.
  • Why "1,000+" and not an exact number. Cloudflare's free plan keeps per-path detail for 8 days, and the unique-device and card beacons are not archived by the nightly collector. 942 uniques were counted through Jul 28 and 53 more in the still-retained Aug 1–8 window; the Jul 29–31 stretch — 396 visits and 152 finished missions — aged out before it could be read, so its new-device count is gone. With that big a gap, 1,000+ is the conservative floor, not a guess.
  • Visits and scores ARE complete. The auto-refreshing collector archives daily mobile visits and the score census to data/history.json in the apollo-telemetry repo, so the daily chart, the waves, the finish totals, and the rank tiers cover the entire run with no gaps.
  • The service worker hides repeat visits. After the first load, the whole site is cached on the phone, so a scout replaying the mission offline generates no new traffic. First visits are counted reliably; browsing depth is undercounted.
  • The pings are all 404s on purpose. The site is static, so there's nothing to receive them — Cloudflare counts the request path at the edge and the 404 costs the scout nothing. Every one of them is disclosed on /privacy.html; if you change a beacon, change that page in the same commit.
  • This page is a snapshot, not a live view. The numbers are baked into the HTML — a static page can't hold the Cloudflare API token, so it can never refresh itself in the browser. The auto-refreshing dashboard lives at robgruhl.github.io/apollo-telemetry (separate repo, GitHub Actions + laptop dispatch, ~every 15–30 min). This snapshot captures the full jamboree arc as of Aug 8; with the event over and traffic down to a trickle, it may well be the final one.
